# Публикация инструкций и статей TrueTell

Сайт остаётся статическим Astro. Тексты находятся в `src/pages/<slug>/index.astro`, метаданные статей — в существующем `src/config/articles.ts`. Content Collections, CMS и второй реестр URL не нужны.

## Добавление материала

1. Создайте страницу по примеру существующего материала через `ArticleLayout` и общие редакционные компоненты. Адрес — `/<slug>/`. Существующие URL не переносите в `/blog/` или `/knowledge-base/`.
2. Добавьте одну запись в `allArticles`:

```ts
{
  title: 'Понятное название материала',
  description: 'Описание содержания для поисковой выдачи.',
  summaryDescription: 'Краткое описание для карточки.', // необязательно
  hrefPath: 'slug/', // без начального /, с завершающим /
  type: 'knowledge', // либо blog
  category: 'Битрикс24', // платформа / тема
  topic: 'Лиды', // конкретная задача
  status: 'draft', // published после редакционной проверки
  indexable: true,
  relatedProduct: '/bitrix24-cleaner/', // либо null
  // publishedAt и updatedAt — только подтверждённые ISO-даты.
  // seoTitle — только когда SEO-заголовок отличается от названия карточки.
  // relatedArticles — необязательный список существующих hrefPath.
}
```

3. На странице читайте `getArticle('slug/')`. Используйте `article.title`, `article.description`, `article.publishedAt`, `article.updatedAt` и `canonicalPath = '/' + article.hrefPath`. Для JSON-LD передавайте `articleType: article.type === 'knowledge' ? 'Article' : 'BlogPosting'`, `publishedDate: article.publishedAt`, `modifiedDate: article.updatedAt`. Не подставляйте дату сборки. Автор и данные компании — из `src/config/company.ts`.
4. Не добавляйте видимую навигацию хлебных крошек: по правилу владельца от 12.10.2026 её нет на всех страницах, включая новые статьи. Навигация — через общую шапку и смысловые ссылки. В корректном `BreadcrumbList` допускается логическая иерархия «Главная → База знаний → Статья» для `knowledge` и «Главная → Блог → Статья» для `blog`. Платформа при необходимости ведёт на якорь реального раздела базы знаний; не создавайте пустые страницы категорий.
5. Связанные статьи получайте через `getRelatedArticles(article.hrefPath)`; описания карточек — `summaryDescription ?? description`. По умолчанию рекомендации ограничены той же платформой/темой. `relatedArticles` позволяет выбрать осмысленные переходы вручную, не копируя названия и описания. При отсутствии подходящих материалов блок скрывается.
6. Укажите связанный продукт, если он действительно помогает в описанной задаче. Страница продукта с `ProductArticles productPath="/product/"` автоматически получит материал после публикации. Не обещайте восстановление данных через Cleaner. Для продукта в разработке прямо обозначайте планируемое поведение.
7. Проставьте `published` после проверки и выполните команды ниже. Каталог, sitemap и внутренний реестр обновятся автоматически; отдельные списки URL не редактируются.

`draft` и `indexable: false` не показываются в каталогах, рекомендациях и XML. Если их Astro-страницы существуют, общий article layout выводит `noindex, nofollow`: это локально проверяемый черновик, а не защита доступа. Для конфиденциального материала не создавайте маршрут в публикуемой сборке. Необязательный `canonical` нужен только для обоснованного исключения дубля; обычная статья использует собственный адрес. Опубликованная запись без существующего маршрута приводит к ошибке сборки.

## Редакционная проверка

Для каждой новой опубликованной статьи типа `blog` в этом же выпуске
подготовьте отдельную версию для Дзена: заголовок, описание, три вводных
абзаца, первый абзац основного текста и начала двух разделов в
`docs/seo/dzen/`. Проверьте продуктовый переход, ссылки, подписи и минимум
две смысловые иллюстрации. Обе картинки должны существовать в сборке как
JPEG, PNG или GIF шириной не менее 700 px; при необходимости подготовьте
отдельный файл для Дзена в `public/dzen-images/`. Это авторская работа:
CI проверяет полноту и собирает RSS, но не пишет текст за редактора.
Подробный процесс и переходные исключения — в
[`docs/seo/dzen/README.md`](dzen/README.md).

`npm run build` формирует `dist/dzen.xml` и локальные копии для редактора
в `.generated/dzen-editor-html/`. Отсутствие адаптации, двух подходящих
изображений или исходного HTML останавливает сборку и CI. Если материал
публикуется в Дзене вручную, укажите `delivery: "manual"` в его адаптации
до подачи RSS, а после публикации сохраните адрес статьи в редакционном
отчёте. Один материал не должен уходить и вручную, и через RSS.

Обязательно запускать параллельно второго независимого агента по [протоколу редакционного ревью](editorial-review-protocol.md). Ревью должно завершиться до публикации: проверить факты по первоисточникам, воспроизводимость шагов, реализованные возможности TrueTell, интент, SEO и изображения; исправить и повторно проверить существенные замечания. Результат с источниками и границами проверки сохранить в отчёте задачи. Поручение владельца от 11.10.2026.

Перед переводом статьи из `draft` в `published` и перед выпуском обновлённой опубликованной статьи обязательно примените навык `humanizer` к окончательному тексту, включая видимый FAQ, подписи, CTA, заголовки и SEO-метаданные. Уберите шаблонные вводные, повторы и необоснованное усиление утверждений; сохраните факты, расчёты, условия, ссылки, URL и голос TrueTell. Если правки не нужны, это тоже результат проверки. Независимое фактологическое ревью остаётся отдельным шагом.

Зафиксируйте результат и границы проверки в отчёте `docs/seo/publications/`. После последней редакции получите отпечаток командой `node scripts/check-article-humanizer.mjs --fingerprint slug/` и добавьте или обновите запись статьи в `docs/seo/humanizer-reviews.json`: `skill: "humanizer"`, дата `reviewedAt`, путь `report` и `fingerprint`. Затем выставьте `published` и выполните `npm run check:article-humanizer` перед сборкой. `npm run build` и CI также запускают эту проверку и останавливаются, если отметки нет или текст/заголовок/описание изменились после неё. Новый отпечаток сам по себе не заменяет повторного чтения и отчёта.

Для базы знаний: краткий ответ сразу; затем реальные шаги, ограничения и частые ошибки. Используйте скриншоты, если они помогают выполнить действие, и проверьте актуальность действий по официальной документации Битрикс24 или МойСклад. Для блога: ответ в начале, практическая польза, чёткая структура, проверенные технические факты, примеры, сравнения и ограничения. Естественный переход к продукту нужен только при наличии связи.

Каждая полноценная SEO-статья содержит как минимум два разных смысловых изображения в разных подходящих разделах. Выбирайте спокойные редакционные иллюстрации и реальные скриншоты по задаче читателя, в палитре TrueTell. Не использовать по умолчанию узкие схемы с крупными заголовками и стрелками. Декоративная заглушка и повтор одного asset не засчитываются. Создаваемые иллюстрации имеют настоящую прозрачность, сохраняющуюся в WebP; реальные скриншоты сохраняют фон и содержимое исходного интерфейса. Используйте общий `ArticleFigure`; подробные экраны открываются через `fullSize`, высокие фильтры — через `portrait`. В подписи обозначайте источник, учебные данные и ограничения примера. Не генерируйте фиктивные скриншоты и не добавляйте вымышленные даты, отзывы или функции.

На всех статьях до 768 px рубрика (`ArticleHero .meta`) и H1 центрированы, основной текст остаётся слева. Отступы блоков задаются общей шкалой: block 32 px, section 40/32 px и shell 56/40 px (desktop/mobile); между абзацами 16 px. Правило владельца от 14.10.2026, обязательное и для будущих страниц. Проверяйте рубрику и промежутки в опубликованном HTML на 390/768/769/1440 px.

Используйте общий article shell, фигуры, таблицы, checklist, FAQ, источники, CTA и related carousel. Не добавляйте React для статического текста. Не переписывайте метаданные уже опубликованного материала без причины.

## Карта сайта и проверки

Единственный генератор — `scripts/seo-integration.mjs` / `scripts/seo-build.mjs`, hook `astro:build:done`. Он читает фактически построенные HTML и их canonical, robots, статус и тип, затем создаёт `dist/sitemap.xml` и `docs/seo/site-map.md`. Общие layout передают служебные метаданные из своего источника. Коммерческие/юридические страницы описываются в своих текущих файлах и общих layout; отдельного массива с копиями их метаданных нет.

Draft, noindex (включая directives Googlebot/Яндекс), редиректы, неканонические копии и 404 исключаются. Юридические страницы сохраняют исходное индексирование. `lastmod` появляется только из записанного `updatedAt`, который article layout передаёт в `article:modified_time`; дата публикации и дата сборки не заменяют дату изменения. Для иных страниц без подтверждённой даты тег отсутствует. XML экранируется и проверяется парсером. Сборка проверяет ссылки на HTML и файлы, наличие опубликованных статей, единственный H1, canonical, title и description.

Генератор выполняется и при прямом `astro build`, и при `npm run build`. В `astro dev` XML не генерируется: проверяйте его после build через preview или в `dist`. Внутренний Markdown остаётся в репозитории и не публикуется. Не переносите его в `public`.

```sh
npm run lint
npm run build
node --test scripts/*.test.mjs
node scripts/indexnow.mjs --check
```

`--check` — локальная проверка, без отправки URL. Проверяйте мобильный, планшетный и настольный вид. Для локальной визуальной проверки доступен `scripts/seo-browser.mjs` с установленным Chromium и Puppeteer; внешние запросы в этом сценарии блокируются. Деплой и отправка sitemap в поисковые системы требуют отдельного разрешения. Наличие URL в XML не означает индексацию в Google или Яндексе.
