# Кабинет заявок TrueTell

## Что готово

Публичный сайт остаётся статическим Astro. PHP-приложение Laravel принимает заявки и обслуживает `/workspace`. В кабинете: общий список, поиск (имя/контакт целиком, источник или окончание номера), фильтры, два статуса, история изменений, сотрудники и светлая/тёмная тема. Контакты, имена, сообщения и TOTP-ключи шифруются Laravel; поиск точного имени/контакта использует HMAC. Источник, путь, UTM и время не шифруются. Второй фактор обязателен для всех.

Telegram выключен по умолчанию. Заявки принимаются без него. Старые заявки после включения автоматически не рассылаются. Новые создают по одному заданию на каждого получателя. Уведомление содержит только номер и защищённую ссылку. При сетевой неопределённости повтор уведомления возможен (Telegram не предоставляет ключ идемпотентности для sendMessage); сама заявка не дублируется.

## Локальная проверка

Нужны Node 24+, PHP 8.3+ с PDO SQLite/MySQL, mbstring, OpenSSL и Composer 2.

```sh
npm ci
npm run build
cd backend
composer install
cp .env.example .env
```

Для локального `.env`: `APP_ENV=local`, `APP_URL=http://127.0.0.1:8088`, `APP_DEBUG=true`, `SESSION_SECURE_COOKIE=false`, `DB_CONNECTION=sqlite`, `DB_DATABASE` — абсолютный путь к отдельному локальному файлу `backend/database/database.sqlite` (создать пустой файл). Затем:

```sh
php artisan key:generate
php artisan migrate
php artisan crm:admin owner@example.com 'Владелец'
cd ..
php -S 127.0.0.1:8088 scripts/serve-crm-dev.php
```

Пароль запрашивается скрыто и не попадает в историю команд. `/workspace/login` → пароль → настройка приложения-аутентификатора через ручной ключ → одноразовый код. Локальные тестовые данные не переносить на хостинг. Форма сайта и PHP должны работать на одном origin; обычный `astro preview` сам по себе не исполняет PHP.

## Размещение на SprintHost

Сайт и backend публикуются единым релизом по SSH. Полная настройка, приватные пути, GitHub Secrets/Variables, cron, резервные копии и откат описаны в [deployment.md](./deployment.md). Старый FTP-сценарий заменён.

После первой установки проверить HTTPS вход, второй фактор, тестовую заявку и смену статуса. Проверить фактический клиентский IP у PHP: формы и вход ограничены по IP. Не доверять произвольному X-Forwarded-For; если виден только адрес прокси, согласовать его доверенные адреса с хостером.

`APP_KEY` сохраняется между релизами. Его потеря лишает доступа к контактам и TOTP. Смена ключа требует APP_PREVIOUS_KEYS и пересчёта HMAC-индексов; не запускать `key:generate` при обновлениях.

## Сотрудники и восстановление

Администратор создаёт отдельные учётные записи сотрудников; пароль передаётся лично по защищённому каналу. Сотрудник на первом входе подключает свой аутентификатор. Все видят все заявки, менять пользователей может только администратор. Отключение сотрудника удаляет его сессии. Управление другими администраторами через UI запрещено; дополнительные администраторы создаются CLI.

При потере пароля/аутентификатора владелец сервера сначала подтверждает личность сотрудника, затем выполняет:

```sh
php artisan crm:reset-access person@example.com
```

Команда требует подтверждения и нового пароля, сбрасывает TOTP и завершает сессии. Публичной регистрации и восстановления через незащищённую ссылку нет.

## Подключение Telegram позже

Создать бота и нажать «Запустить» в личном чате. В приватном `.env`:

```dotenv
TELEGRAM_ENABLED=true
TELEGRAM_BOT_TOKEN=<токен>
TELEGRAM_CHAT_IDS=<твой chat_id>
```

Затем `php artisan config:cache`. Создать новую тестовую заявку, выполнить `php artisan crm:deliver` или дождаться cron. Для группы добавить её chat_id; для нескольких получателей перечислить ID через запятую. Ничего не отправляется в произвольный chat_id из формы посетителя.

Отправка: максимум 10 заданий за запуск, таймаут HTTP 8 секунд, до 5 попыток с задержкой; HTTP 429 учитывает retry_after. После 5 неудач запись остаётся в `telegram_deliveries` с `failed_at` и кодом ошибки без токена/контактов. Контролировать cron лог и количество failed_at. Для повторной доставки после устранения проблемы уполномоченный оператор может сбросить attempts=0, failed_at=NULL, next_attempt_at=NOW() у конкретного задания в БД. Не сбрасывать sent_at у успешных заданий.

## Резервные копии и данные

Ежедневная зашифрованная резервная копия MySQL с доступом только владельца, хранение вне public_html; отдельно — APP_KEY и настройки. Проверить восстановление в отдельную базу до ввода в эксплуатацию. Срок хранения резервных копий определить по рабочему процессу. Удалять заявки после достижения цели обработки или подтверждённого отзыва согласия; это операция ответственного сотрудника, автоматическое удаление по возрасту не включено. При восстановлении резервной копии повторно применить ранее выполненные запросы на удаление. Для удаления конкретной заявки по подтверждённому запросу использовать её UUID и транзакционное удаление из leads: audit/deliveries удалятся каскадно. Не удалять общую БД и не хранить выгрузки на публичном сайте.

## Проверки изменений

```sh
npm run lint
npm run build
node --test scripts/*.test.mjs
node scripts/indexnow.mjs --check
cd backend
php artisan test
vendor/bin/phpstan analyse --memory-limit=512M
vendor/bin/pint --test
```

CI проверяет сайт и backend, запускает PHP-тесты на SQLite и MySQL 8, затем собирает и развёртывает общий релиз. Локальные feature-тесты по умолчанию используют SQLite in-memory; настройки конкретного SprintHost требуют проверки при установке. Бот не подключён, его HTTP-поведение проверяется подменёнными ответами, реальные сообщения не отправляются.
